# 安全组与防火墙规则：只开放必要端口，避免把云服务器直接暴露到公网

云服务器买好以后，控制台里往往已经有一套能连上的规则：22、3389，有时还有 80、443，授权对象是 `0.0.0.0/0`。另一种常见做法是把 3306、5432、1433、6379 这些数据库端口也授权给 `0.0.0.0/0` 或 `::/0`。另一类问题是只改了一层。安全组收紧了，子网上的网络 ACL 仍是默认放行，或者正好相反：ACL 已经拒绝，安全组看起来却是通的。还有一类是地址族没一起改。IPv4 收成办公网网段之后，IPv6 的 `::/0` 或一键放通里的 IPv6 规则还在。

这篇只写云服务器和 VPC 上的入方向、出方向流量过滤：安全组、网络安全组、网络 ACL、VPC 防火墙规则，以及文档里写明要和它们一起看的防火墙策略。登录多因素认证和最小权限见 [云账号登录和权限怎么收紧](cloud-account-mfa-least-privilege.md)。计算、磁盘、公网流量和快照费用见 [云服务器账单为什么超预算](cloud-server-bill-over-budget.md)。闲置公网 IP、负载均衡和 NAT 网关的空转计费见 [闲置公网 IP、负载均衡与 NAT 网关](idle-public-ip-lb-nat-cleanup.md)。对象存储的私有桶与临时链接、存储类型，以及 CDN 的流量和回源，分别见 [对象存储私有桶与临时访问链接](object-storage-private-bucket-presigned-url.md)、[对象存储存储类型与生命周期](object-storage-storage-class-lifecycle.md) 和 [CDN 费用配置与防超支](cdn-cost-configuration.md)。那些内容这里不重复。

## 先看这几件事

1. 先分清过滤挂在哪一层，再改规则。阿里云安全组作用在弹性网卡上，网络 ACL 作用在交换机上。腾讯云安全组作用在云服务器、负载均衡、云数据库等实例上，网络 ACL 作用在子网上。AWS 安全组关联到资源，网络 ACL 关联到子网。Azure 网络安全组可以关联到子网，也可以关联到虚拟机的网络接口，两边的先后顺序不同。Google Cloud 的 VPC 防火墙规则配置在网络上，连接是否放行按实例执行。只改其中一层，另一层仍按它自己的默认规则工作。
2. “默认”不是各云共用的一个词。新建一个没有自定义允许规则的组，和购买时自动生成的默认安全组、控制台模板、一键放通，经常不是同一套规则。阿里云默认安全组会放行任意 IPv4 来源的 22、3389 和 ICMP。腾讯云未添加规则时拒绝全部出入站，但 API 购买云服务器时若不指定安全组，系统生成的默认安全组是放通所有 IPv4。AWS 新建安全组没有入站规则，出站却有一条允许全部；VPC 自带的名为 default 的安全组又是另一套。Google Cloud 的 default 网络预置了来自 `0.0.0.0/0` 的 SSH 和 RDP。看到“默认拒绝”之前，先对上是哪一种默认。
3. `0.0.0.0/0` 和 IPv6 全网地址要分开核对。阿里云、腾讯云、AWS、Google Cloud 已打开的页面都把它们写成两种匹配。只改 IPv4 规则，不会自动改掉 IPv6 规则。反过来，有的默认源只覆盖 IPv4：Google Cloud 在入方向规则省略来源时，默认源是 `0.0.0.0/0`，该页写明这个默认值不包含 IPv6。
4. 有状态的过滤会记住已经允许的会话，回包不必再写一条。无状态的网络 ACL 不会。入方向放行了服务端口之后，响应要靠出方向（或另一侧的入方向）明确放行客户端临时端口。安全组看起来已经放行、跨子网却超时，先看子网这一层有没有无状态规则。
5. 公网 IP 还在，不等于端口已经对公网开放；端口收紧，也不等于这张公网 IP 的保有费已经停。要不要保留公网 IP、负载均衡和 NAT，按 [闲置公网 IP、负载均衡与 NAT 网关](idle-public-ip-lb-nat-cleanup.md) 核对。这篇只判断流量能不能进来、能不能出去。
6. 管理端口和业务端口分开授权。已打开的阿里云案例、AWS 安全组规则示例和 Google Cloud 的 default 网络预置规则，都把 22、3389 写成需要单独处理的端口。数据库端口在阿里云案例和 AWS 示例里，授权对象是具体 IP 或另一层的安全组，不是全网。腾讯云这次打开的概述和添加规则页没有单独的 3306 示例，不把阿里云的端口表套过去。

### 安全组作用在弹性网卡上

[安全组概述](https://help.aliyun.com/zh/ecs/user-guide/security-groups-1/)（更新时间：2026-06-25 02:05:54）把安全组写成控制 ECS 实例出入站流量的虚拟防火墙。创建实例时要指定一个或多个安全组。实例关联的安全组，规则作用于主网卡；专有网络实例的其他弹性网卡可以指定另一套安全组。安全组只能在所属 VPC 里使用，虚拟交换机和安全组必须属于同一个 VPC。实例或弹性网卡至少关联一个安全组。创建实例时如果没有指定，主网卡会关联到默认安全组。

[使用安全组](https://help.aliyun.com/zh/ecs/user-guide/start-using-security-groups)（页上未见更新日期）把同一件事写进控制台路径：在实例详情的安全组页签里更换安全组，改的是主网卡；辅助弹性网卡要在弹性网卡页面单独更换。购买实例时如果在快捷配置里勾选端口，勾选结果是允许所有 IP 地址（`0.0.0.0/0`）访问该端口。该页写明，勾了 SSH（22）或 RDP（3389）之后，应在实例创建后改成只允许安全的 IP。购买时新建安全组不能在这一步做精细规则，创建后再改。

安全组分为普通安全组和企业级安全组，概述页写明两者均免费。普通安全组支持组内互通，也支持把安全组 ID 写成授权对象，能容纳的私网 IP 数量少于企业级安全组。企业级安全组不支持组内互通，也不能把安全组 ID 写成授权对象。同一块弹性网卡上的多个安全组只能是一种类型，不能混用。[普通安全组与企业级安全组](https://help.aliyun.com/zh/ecs/user-guide/basic-security-groups-and-advanced-security-groups)（页上未见更新日期）给出容量：VPC 下普通安全组 6,000 个私网 IP，按网卡上的主私网 IPv4、IPv6、辅助 IPv4、前缀等合计；企业级安全组 65,536，按关联的弹性网卡张数合计。普通安全组里，授权对象为安全组的规则最多 20 条。企业级安全组这一项是 0 条，也不能被别的安全组当成授权对象。

托管安全组由云产品创建。概述页写明，`DescribeSecurityGroups` 的 `ServiceManaged` 为 `True`，或控制台提示云产品托管、不支持修改时，只能查看，不能按自定义安全组那样改规则。使用安全组页还写明，托管安全组不能删除。

国际站 [Security group overview](https://www.alibabacloud.com/help/en/ecs/user-guide/overview-44)（Last Updated: Jun 25, 2026）用 basic、advanced 对应普通、企业级，API 里的 `SecurityGroupType` 分别是 `normal` 和 `enterprise`。主网卡、辅助网卡、未指定安全组时使用该 VPC 的默认安全组、托管安全组只读，与中国站概述一致。国际站这篇没有写出 6,000 和 65,536，容量数字只以中国站对比页为准。

### 不添加规则时的隐式默认，和默认安全组不是同一套

[安全组规则](https://help.aliyun.com/zh/ecs/user-guide/security-group-rules)（页上未见更新日期）写明：一条规则都没添加时，安全组仍有不可见的默认访问控制规则。普通安全组入方向默认只放行同组其他实例来的内网流量，出方向放行所有流量。企业级安全组入方向和出方向默认都不放行。普通安全组的组内连通策略默认是组内互通。不需要互访时，该页建议改成组内隔离。

普通安全组与企业级安全组页把排序写得更细。组内互通时，入方向先放行同组其他实例的内网访问，这条不可见规则不受自定义规则影响；然后才是自定义规则；都没匹配上则拒绝。出方向先看自定义规则，没匹配上则允许。改成组内隔离之后，同组内网不再被这条不可见规则放行，入方向没匹配上就拒绝，出方向仍然是没匹配上就允许。企业级安全组入方向、出方向都是自定义规则优先，没匹配上则拒绝，也不能把策略改成组内互通。

使用安全组页补充：实例关联了多个安全组时，只要其中任何一个普通安全组仍是组内互通，实例之间就可以内网互通。组内隔离之后，要互访就得再写允许规则。[网络连通性常见问题](https://help.aliyun.com/zh/ecs/network-connectivity-faqs)（页上 H1 为「网络连通性常见问题」，未见更新日期）写的是同一件事的后果：同组默认互通时，直接加一条组内拒绝并不会生效，要先改成组内隔离，再用允许规则放行需要的端口和来源。

[默认安全组](https://help.aliyun.com/zh/ecs/user-guide/default-security-groups)（页上「更新时间」栏为空）描述的是另一套可见规则。创建实例时未指定安全组，阿里云把实例放进默认安全组；默认安全组不存在或装不下更多实例时，会新建一个。每个 VPC 各自有自己的默认安全组。它的类型是普通安全组，因此上面的组内互通和出方向未命中即允许仍然适用。在此之上，默认入方向还有三条允许，优先级都是 100，授权对象都是 `0.0.0.0/0`：TCP 22/22、TCP 3389/3389、ICMP（IPv4）的 `-1/-1`。该页用「重要」写明，这会让任何人都能尝试连接实例，可能成为暴力破解的目标，并建议按业务新建安全组或修改这些规则，只放通指定源地址。2020 年 5 月 27 日以前创建的默认规则，优先级是 110。`CreateInstance` 可以不指定安全组并落入默认安全组；`RunInstances` 必须指定已有安全组。控制台快速购买同样会加入默认安全组。

国际站 [Default security groups](https://www.alibabacloud.com/help/en/ecs/user-guide/default-security-groups)（Last Updated: Dec 09, 2024）的三条入方向规则、优先级 100、`0.0.0.0/0`、2020-05-27 以前为 110，以及 `CreateInstance` 与 `RunInstances` 的差别，与中国站默认安全组页一致。

网络连通性常见问题页还有两句，和默认安全组页的表不是同一张表，这里分开保留：

- 通过控制台在一个地域首次创建实例、尚未创建安全组、因而使用系统自动创建的默认普通安全组时，入方向放行 ICMP（IPv4）、SSH 22、RDP 3389，授权对象为 `0.0.0.0/0`，优先级 100，并且「还可以勾选」放行 HTTP 80 和 HTTPS 443。出方向允许所有访问。
- 在控制台上创建安全组并采用该页所谓的默认规则时，入方向放行 ICMP（IPv4）、22、3389、80、443，授权对象为 `0.0.0.0/0`。

默认安全组专页的表里没有 80 和 443。80、443 出现在常见问题页的「还可以勾选」和「创建安全组时的默认规则」两句里。不把这两句合并成“默认安全组一定放行 80/443”。

### 入方向、出方向和优先级

安全组规则页写明，VPC 里的规则分入方向和出方向，同时控制公网和内网。安全组有状态。一个会话最长保持 910 秒。允许并建立会话之后，同一会话的回包默认放行。因此使用安全组页写：有状态规则只需配置入方向，对应的出方向响应由系统放行。这句说的是响应，不是任意出方向访问。出方向没写允许规则时，普通安全组仍会放行未匹配的出方向流量，企业级安全组不会。

修改规则，或更换网卡关联的安全组时，如果修改前后的行为没有变，已经建立的会话不受影响。若放行依赖普通安全组的组内互通，又不希望断开已有会话，规则页给出的顺序是：先加入新安全组，等待约 10 秒，再离开旧安全组。

自定义规则的优先级是 1～100，数值越小越优先。多个安全组的规则先汇总再排序：先按优先级从小到大，同优先级时拒绝排在允许之前。流量从上到下匹配，命中第一条就执行并停止。全部自定义规则都未命中，才落到上面的隐式默认。

规则由协议、目的端口、授权对象、允许或拒绝、优先级和方向组成。协议名可以是 TCP、UDP、ICMP（IPv4）、ICMP（IPv6）、GRE；部分地域还可以写 0～255 的 IANA 协议号。该页列出的协议号地域包括华北 5（呼和浩特）、华北 1（青岛）、菲律宾（马尼拉）、英国（伦敦）、马来西亚（吉隆坡）、美国（硅谷）、新加坡。其他地域是否支持，以该页当前名单为准，这里不外推。TCP 和 UDP 的端口写成 `22/22` 或 `8000/9000`；其他协议是 `-1/-1`。

授权对象可以是 IPv4 或 IPv6 地址、CIDR、安全组 ID、前缀列表。安全组 ID 匹配的是目标安全组里实例的内网 IP，不是公网 IP。企业级安全组不能使用这种授权对象，见上一节。控制台里的一般规则，入方向是源地址加目的端口，出方向是目的地址加目的端口。需要同时限制源端口、目的端口和两端地址时，规则页写的是用 API 配置五元组。五元组里如果要指定某一台 ECS，写它的私网 IP。固定公网 IP 和 EIP 是公网网关上的 NAT 地址，安全组看的是网卡上的私网 IP。

有几类流量，规则页写明安全组会默认放行，自定义规则拦不住：底层变更时的按需 Ping 探测；路径 MTU 发现所需的 ICMP 差错报文；经 ALB、NLB 或 CLB 转到后端 ECS 的流量，这时由负载均衡上的安全组或访问控制策略来控制；访问元数据服务 MetaServer `100.100.100.200` 的出站流量。使用安全组页的常见问题还写：把规则设成全部拒绝之后，若仍要允许阿里云内部的健康检查和可用性监控，添加入方向允许 `100.64.0.0/10`。这是该页给出的地址段，不把它写成其他云的健康检查网段。

TCP 25 在规则页被写成默认受限，并建议改用 465 和 SSL。使用安全组页的限制表对普通安全组和企业级安全组都写了这一条。这里不展开邮件发送的配置。

规则数量有两页不同的上限，分开保留，不取其中一边当作现行统一配额：

- 安全组规则页：单张弹性网卡最多 10 个安全组；该网卡关联的全部安全组，入方向加出方向，规则总数上限 2,000。
- 使用安全组页的限制表：单张网卡最多 10 个安全组；全部关联安全组的入方向与出方向规则之和，上限 1,000。普通安全组和企业级安全组这一项相同。
- 国际站 [Security group rules](https://www.alibabacloud.com/help/en/ecs/user-guide/security-group-rules)（Last Updated: Oct 12, 2026）：同样是最多 10 个安全组，规则总数上限写的是 1,000。

前缀列表和端口列表占用的配额，按列表的最大条目数计算，不按里面已经填了几条计算。使用安全组页写明安全组本身不收费。同一页写安全组快照会把备份放进对象存储 OSS，OSS 按量计费，因此快照会产生存储和请求费用。快照在规则变更约 5 分钟后创建，5 分钟内多次变更只按首次变更前的规则做一次；保留天数 1～30，默认 1 天。对象存储怎么计价见存储类型一文，这里不抄单价。

### 22、3389 和数据库端口

[安全组应用指导和案例](https://help.aliyun.com/zh/ecs/user-guide/security-groups-for-different-use-cases)（页上未见更新日期）把规划写成：公网服务和内网服务用不同安全组；不同应用分开；生产、测试、开发分开。公网服务只开必要端口。数据库和缓存建议放在没有公网访问的实例上，用另一个安全组的 ID 做内网授权。不需要公网的实例不分配公网 IP。只需要出方向访问公网时，该页建议用 NAT 网关做 SNAT，避免为了出网而绑上公网 IP 或 EIP。NAT 和 EIP 停用后是否还在计费，见闲置公网资源一文，这里不重复。

连接实例时，该页写的优先顺序是 Workbench、会话管理工具或跳板机。没有公网或要访问私网服务时，可以用会话管理 CLI 的端口转发。排查问题时，该页不建议临时分配公网 IP 或挂上 EIP。

使用方式被写成白名单：默认拒绝，只添加允许规则。警告写明，授权对象为 `0.0.0.0/0` 或 `::/0` 表示允许所有 IP，只在必须对公网开放时使用，并且只开必要端口。概述页的最佳实践用 22 端口举例：只允许特定 IP，而不是 `0.0.0.0/0`。使用安全组页的端口表把 22、3389 和面板端口（示例是 8888）的授权对象写成办公网或固定公网 IP，并写明不建议长期使用 `0.0.0.0/0`；80 和 443 在公网建站时可以使用 `0.0.0.0/0`。3306 的建议是在数据库安全组的入方向授权源安全组，不对公网开放。

案例页给出的示例，数字是示例，替换成实际地址之后才能用：

- Web：入方向允许，优先级 1，TCP 80 和 443，源 `0.0.0.0/0`。其他端口保持关闭。
- 远程登录：入方向允许，优先级 1，Linux 用 22，Windows 用 3389，源是某个具体地址，页上的占位是 `192.168.XX.XX`。通过公网 IP 或 EIP 使用 Workbench 时，中国站案例列出的授权对象是 `47.96.60.0/24`、`118.31.243.0/24`、`8.139.112.0/24`、`8.139.99.192/26`。通过 VPC 私网 IP 使用 Workbench 时，授权对象是 `100.104.0.0/16`。
- 数据库：MySQL 3306 的示例源是 `172.16.XX.XX`，Oracle 1521 是 `192.168.XX.XX`，SQL Server 1433 是 `192.168.XX.XX/16`，PostgreSQL 5432 是一个安全组 ID，Redis 6379 是「账号 ID/安全组 ID」。优先级都是 1 的允许。若已有 `0.0.0.0/0`，该页说不需要公网时可以加拒绝规则，并把 MySQL 3306 的拒绝优先级写成 100。
- 不同安全组的内网互访：同一 VPC、同一账号时授权对象填安全组 ID；跨账号时填「账号 ID/安全组 ID」。实例在不同 VPC 时，安全组单独做不到内网互通，案例页指向对等连接、私网连接或云企业网。企业级安全组不能把安全组 ID 当授权对象，这条以普通安全组与企业级安全组页为准。案例里的安全组 ID 示例不能直接用在企业级安全组上。
- 出方向白名单示例：优先级 1 允许访问指定 IP 的 80 和 443，优先级 2 拒绝 `0.0.0.0/0` 的全部协议。该页提醒，数值越小越优先，同优先级拒绝优先。因此拒绝全部的那条要使用更大的数字，指定网站的允许才能先命中。

把案例里的「3306 拒绝、优先级 100」和规则页的匹配顺序放在一起看：优先级 1 的允许会先被检查，命中后就停止。一条优先级 100 的拒绝，只能排在同为 100 的允许之前（同优先级时拒绝靠前），不能压过优先级 1～99 的允许。默认安全组里 22 和 3389 的允许本身就是优先级 100。若后来又加了一条更小数字的全网允许，仅按案例那句把拒绝设为 100，不会先命中。这是两页原文合在一起的读法，不是另一份官方修订。

国际站 [Security group guidelines and use cases](https://www.alibabacloud.com/help/en/ecs/user-guide/security-groups-for-different-use-cases)（Last Updated: Jun 25, 2026）的 Web、远程登录、数据库端口和出方向白名单示例，结构与中国站相同。出方向那一节的英文写的是 basic security group 默认允许全部出方向，中国站案例开头写的是「安全组出方向规则默认允许访问」，没有在这一句里加上「普通」。中国站规划小节已经写了企业级默认拒绝出方向。两句都保留。Workbench 的网段不同：国际站公网连接写的是 `161.117.0.0/16`，私网连接同样是 `100.104.0.0/16`。不要把中国站的四段公网前缀写进国际站账号，也不要反过来。

### IPv6

规则页的授权对象同时接受 IPv6 地址和 IPv6 CIDR，并会做标准化，例如 `2408:180:0000::1` 收成 `2408:180::1`。案例页和概述页把 `::/0` 与 `0.0.0.0/0` 并列，都视为所有 IP。ICMP 在 IPv6 环境要选 ICMP（IPv6），端口 `-1/-1`。

默认安全组页的三行表只有 IPv4：22、3389 和 ICMP（IPv4），授权对象是 `0.0.0.0/0`。该页没有列出对应的 `::/0` 行。收紧默认安全组时，只改这三行，并不能说明 IPv6 入方向的状态；IPv6 有没有单独的允许，要在当前安全组的 IPv6 规则里再看一遍。这次打开的默认安全组页没有写“默认同时放行 IPv6 的 22/3389”。

### 网络 ACL

[网络 ACL](https://help.aliyun.com/zh/vpc/network-acl-overview)（页上「更新时间」栏为空）作用在绑定的交换机内的弹性网卡上，能管到依赖弹性网卡的资源，页上举例 ECS、ECI、NLB。RDS、CLB 不依赖弹性网卡，网络 ACL 不管它们；RDS 用白名单，CLB 用访问控制策略。绑定了网卡可见模式 EIP 的辅助弹性网卡，也不受网络 ACL 控制。经私网连接 PrivateLink 访问云服务时，流量经过终端节点网卡，会受网络 ACL 管控。

规则无状态。入方向允许了请求，响应不会自动允许，要另写出方向，放行回到客户端临时端口的流量。该页给出的临时端口：Linux `32768/61000`，Windows Server 2003 `1025/5000`，Windows Server 2008 及更高版本 `49152/65535`，NAT 网关 `1024/65535`。为了覆盖不同客户端，可以把临时端口设为 `1024-65535`。入方向规则只写源地址，出方向规则只写目的地址，一条规则不能两端都写。端口范围匹配的是目的端口。拒绝是 drop，发起端收不到响应，表现是超时或连不上。

从生效顺序 1 开始匹配，命中第一条就执行。要在大范围允许里挖掉个别端口，拒绝规则的顺序要排在允许之前。

为一个只有 IPv4 的 VPC 创建网络 ACL 时，入方向和出方向都会带上三类规则：

- 云服务规则，优先级固定最高，不能改、不能删。放行私网 DNS `100.100.2.136`、`100.100.2.138`，以及 MetaServer `100.100.100.200`。
- 自定义规则，允许所有 IPv4。页上的理由是创建后不要打断同一 VPC 里交换机之间的私网互通。
- 系统规则，拒绝还没被其他规则匹配的 IPv4，优先级固定最低，不能改、不能删。

VPC 开启了 IPv6 之后，入方向和出方向再各加一条允许所有 IPv6 的自定义规则，以及一条拒绝所有 IPv6 的系统规则。因此，刚创建并绑定的网络 ACL，在你改掉那条允许全部的自定义规则之前，不是“默认拒绝业务流量”。它和安全组的企业级默认拒绝、也和腾讯云网络 ACL 的默认拒绝，不是同一句话。

每个交换机只能绑一个网络 ACL，一个网络 ACL 可以绑多个交换机。规则改动会自动作用到已绑定的交换机。控制台路径写在该页：专有网络控制台的网络 ACL 页面，先选地域再创建，所属 VPC 要选交换机所在的 VPC；在已绑定资源页签关联交换机，或在交换机详情里绑定。`UpdateNetworkAclEntries` 是全量更新，只传入新规则会删掉没被带上的旧规则。国际站 [Network ACLs](https://www.alibabacloud.com/help/en/vpc/network-acl-overview)（Last Updated: Oct 26, 2026）对无状态、默认允许全部 IPv4、开启 IPv6 后允许全部 IPv6、云服务规则和系统规则，以及临时端口数字，与中国站一致。国际站把 Linux 临时端口写成 `32768-61000`，中国站写成 `32768/61000`，数字相同，分隔符不同。

中国站配额：单个网络 ACL 入方向、出方向默认各 20 条；VPC 开了 IPv6 时，IPv4 和 IPv6 的入方向、出方向默认各 20 条。单个 VPC 最多 20 个网络 ACL。该页写明网络 ACL 不收费，并列出公有云、金融云和政务云的支持地域。国际站配额相同，也写不收费；这次打开的国际站地域表没有单列金融云和政务云，不把中国站那两段名单套到国际站账号。

使用安全组页用三行对比了两层：安全组在弹性网卡、有状态、做实例上的细规则；网络 ACL 在子网、无状态、做子网边界。安全组放行而网络 ACL 仍是允许全部时，子网边界没有额外收紧。网络 ACL 写成拒绝而安全组没有相应允许时，流量也到不了实例。

## 腾讯云

以下只来自中国站 cloud.tencent.com。国际站两个地址这次都是 404，下面的模板名称、默认规则和工作台路径不要套到国际站账号。

### 安全组是有状态的实例防火墙

[安全组概述](https://cloud.tencent.com/document/product/215/20089)（最近更新时间：2026-10-28 15:17:00）把安全组写成有状态的虚拟防火墙，用来控制云服务器、负载均衡、云数据库等实例的出入流量。同一地域、同样隔离需求的实例可以放进一个安全组。未添加任何规则时，默认拒绝所有出站和入站，需要自行添加允许规则。已经允许的入站流量，回包自动允许；已经允许的出站流量，对应的响应也自动允许。规则修改后立即生效。

规则由三部分组成：来源或目标（单个 IP、地址段或安全组）、协议和端口、允许或拒绝。组内规则按列表从上到下，顶端优先。冲突时匹配位置更前的规则。命中一条之后，不再匹配该组里后面的规则。

一个实例可以绑定多个安全组，多个组也按从上到下匹配，顺序可以调整。概述页的说明是：如果较高优先级的安全组里没有任何规则，会继续看下一个安全组，直到遇到第一个含有规则的安全组，再按那个组内部的顺序执行。一个空规则的高优先级组，不会把后面已有规则的组整个挡住。该页同时建议不要给一个实例绑过多安全组，避免规则冲突导致不通。

[添加安全组规则](https://cloud.tencent.com/document/product/215/39790)（最近更新时间：2026-05-11 14:15:46）写明安全组同时管公网和内网，并写“入方向大多采取拒绝访问策略”。控制台路径是：登录安全组控制台，选地域，在目标安全组的操作列单击修改规则，再进入站或出站。来源可以是 IP 或 CIDR、参数模板、安全组 ID，或当前登录控制台的公网 IP。`0.0.0.0/0` 表示所有 IPv4。引用安全组 ID 时，匹配的是该安全组所绑定云服务器和弹性网卡的内网 IP，不包括外网 IP，也不包括该页所写的 PAAS 服务和 CLB 的 IP；绑到公网 CLB 时，引用安全组 ID 不生效。策略默认选项是允许。拒绝会直接丢弃数据包，不返回响应。

### 模板和 API 默认安全组会放行，不是“未添加规则”

概述页列出新建安全组时的两种模板：

- 放通全部端口：放通所有出站和入站流量。
- 放通 22、80、443、3389 端口和 ICMP 协议：放通 TCP 22（Linux SSH）、80 和 443（Web）、3389（Windows 远程登录）、ICMP（Ping），以及内网（私有网络网段）。

添加规则页写明，选了这两种模板，系统会按模板给相应协议端口自动加规则。模板说明里没有单独写出授权对象是 `0.0.0.0/0` 还是 VPC 网段，这里不补。可以按概述页另行建自定义安全组。

另一条默认出现在购买路径。概述页写：调用 API 购买 CVM 时建议指定安全组；未指定时使用系统自动生成的默认安全组，默认规则为放通所有 IPv4。默认安全组创建后可以改。这句里的“所有 IPv4”和“未添加任何规则时默认拒绝”都在同一篇概述里，适用条件不同：前者是没指定安全组时系统生成的默认安全组，后者是一个还没有任何规则的安全组。

添加规则页的「一键放通」适用于一组固定端口：22、3389、ICMP、ICMPv6、80、443、20、21。该页写明一键放通已经同时包含 IPv4 规则和 IPv6 规则。因此只检查 IPv4 是否还对全网开放，会漏掉这一键放通带上的 IPv6。页上没有把一键放通的来源地址写成 `0.0.0.0/0` 或 `::/0` 的表格，来源以控制台当前生成的规则为准，不在这里补一行。

概述页的实践建议是：防护策略变了，优先改现有安全组里的规则，而不是再新建一个组；相同防护需求的实例放进同一个组；改规则前先导出备份，有问题再导入恢复。该页没有给出 MySQL 或其他数据库端口的示例。数据库端口要不要对公网开放，不能从这篇概述推导出一条腾讯云专用的端口表。阿里云案例里的 3306、5432 不要抄到腾讯云安全组上。

### 网络 ACL 是可选的子网层，而且无状态

[规则概述](https://cloud.tencent.com/document/product/215/20088)（最近更新时间：2025-09-09 16:57:22）把网络 ACL 写成子网级别的可选层，可以按协议和端口控制进出子网的流量。多个子网可以关联同一个 ACL。该页的场景是 Web、逻辑、数据三层子网：让 Web 子网和数据子网不能互访，只让逻辑层访问这两层。

规则包含源或目标 IP、协议、端口、允许或拒绝。入站填源 IP 和目标端口，出站填目标 IP。地址可以是单个 IPv4、单个 IPv6、CIDR、`0.0.0.0/0`，或表示所有 IPv6 的 `0::0/0` 与 `::/0`。端口可以是单个端口、连续端口或 ALL。

每个网络 ACL 创建后有两条默认规则，不能修改、不能删除，优先级最低。入方向是协议 ALL、端口 ALL、源 `0.0.0.0/0`、拒绝。出方向是协议 ALL、端口 ALL、目标 `0.0.0.0/0`、拒绝。默认规则表里没有 `::/0` 那一行。自定义规则可以写 IPv6，但是“默认规则已经拒绝全部 IPv6”不是这张表上的句子，这里不补。

同一页有两句匹配说明，不合成一条算法。一句是：从列表顶端逐条匹配，匹配成功则允许通过，不再匹配后面的规则。另一处是应用示例：要拒绝 `192.168.200.11/24` 访问 80，同时允许其他来源访问所有端口，应先写拒绝，再写允许全部。示例的意图是位置更前的拒绝先生效。概述页的对比表也写了，规则冲突时应用位置更前的规则。只采用“匹配成功则允许通过”这一句，会读不懂示例里的拒绝；只采用示例，又和“则允许通过”的字面不完全一样。改规则时以该页最新正文和控制台里实际命中的那一条为准，不要按其他云的“同优先级拒绝优先”去套。

和安全组的对比，该页表写的是：安全组管实例，网络 ACL 管子网；两者都支持允许和拒绝；安全组有状态，回包自动允许；网络 ACL 无状态，回包必须被规则明确允许；安全组要在创建实例时指定，或创建后再关联，才会作用到实例；ACL 绑定子网后自动作用到该子网里的云服务器、云数据库等实例。

因为无状态，只在服务子网的入站放行 TCP 3306 或 80，回包的目的端口是客户端的临时端口，不是服务端口。规则概述没有给出 Linux 或 Windows 的临时端口数字。不把阿里云或 AWS 页上的 `1024-65535`、`32768-61000` 写成腾讯云的官方范围。要放行回包，得在出站（以及流量进入对端子网时的入站）按实际临时端口写允许，并且排在默认拒绝之前。只绑了 ACL、没有在默认拒绝上面加允许时，进出该子网的流量会落到默认拒绝。

### 安全组和云防火墙不是同一层

概述页把云防火墙写成另一款产品：安全组在 CVM 等云产品边界，做安全组之间的访问控制；云防火墙在 VPC 之间或互联网边界。该页列出安全组不够用时才考虑云防火墙的场景，包括看资产暴露和漏洞、按域名做主动外联控制、按区域封禁访问。这里不展开云防火墙的购买和策略语法。实例端口是否对公网开放，先看安全组，再看子网有没有绑网络 ACL。

## AWS

以下来自 docs.aws.amazon.com 的全球文档，没有打开 docs.amazonaws.cn。中国区账号不要把下面的默认规则直接当成中国区文档已经核对过。

### 安全组只写允许，并且有状态

[Control traffic to your AWS resources using security groups](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html)（页上未见更新日期）写明：安全组控制与它关联的资源的入站和出站。VPC 创建时自带一个默认安全组，还可以再建别的安全组。入站规则指定来源、端口范围和协议，出站规则指定目的、端口范围和协议。该页写使用安全组没有额外费用。

安全组有状态。从实例发出的请求，响应可以回来，不必再有一条入站规则；入站被允许的流量，响应可以离开，不必再有一条出站规则。安全组不过滤该页列出的这些流量：Amazon DNS、Amazon DHCP、EC2 实例元数据、ECS 任务元数据端点、Windows 实例的许可证激活、Amazon Time Sync Service，以及默认 VPC 路由器使用的保留地址。想限制元数据访问，不能靠在安全组里加一条拒绝，因为安全组根本不能写拒绝，而且元数据在这份排除列表里。

[Security group rules](https://docs.aws.amazon.com/vpc/latest/userguide/security-group-rules.html)（页上未见更新日期）把规则特性写成：

- 只能指定允许规则，不能指定拒绝规则。
- 新建安全组没有入站规则，因此在你添加入站规则之前，不允许入站。
- 新建安全组有一条出站规则，允许资源的全部出站。可以删掉它，再写成更窄的允许。如果没有任何出站规则，不允许出站。
- 一个资源关联多个安全组时，各组规则汇总成一套，用来决定是否允许。规则页没有给安全组规则写优先级数字。这和阿里云的 1～100、Azure 的 100～4096、Google Cloud 的 0～65535 不同。
- 规则增删改会自动作用到所有关联资源。部分变更对已有流量的影响取决于连接跟踪。连接跟踪专页这次没有打开，不写超时秒数。

来源或目的可以是单个 IPv4（必须 `/32`）、单个 IPv6（必须 `/128`）、IPv4 或 IPv6 CIDR、前缀列表 ID、安全组 ID。引用安全组时，匹配的是被引用组里实例的私网 IP。同一 VPC、对等连接或（入站规则下）Transit Gateway 连接的 VPC 之间可以引用。该页写明一个限制：流量若被路由到中间设备再转发，只引用对方安全组 ID 并不能放行，要引用对方私网 IP 或子网 CIDR。

规则条数按来源类型计权：CIDR 和安全组引用各算 1 条；客户托管前缀列表按前缀列表的最大容量计；AWS 托管前缀列表按该前缀列表的权重计。具体配额页这次没有逐项打开，不填每个 VPC 能建多少个安全组。

### 名为 default 的安全组，和新建的空入站安全组

[Default security groups for your VPCs](https://docs.aws.amazon.com/vpc/latest/userguide/default-security-group.html)（页上未见更新日期）写明，默认 VPC 和你新建的 VPC 都有一个名为 default 的安全组。创建资源时如果没关联安全组，例如启动 EC2 没指定，就会关联这个默认安全组。可以改它的规则，不能删除它；尝试删除会返回 `Client.CannotDelete`。该页建议为具体资源另建安全组，而不是继续使用默认安全组。

默认入站只有一条：来源是这个安全组自己的 ID，协议和端口都是全部，也就是允许关联到本组的资源互相访问。默认出站有一条目的 `0.0.0.0/0`、协议和端口全部的允许。若 VPC 有关联的 IPv6 CIDR，再增加一条目的 `::/0` 的全部出站允许；没有 IPv6 CIDR 就不会有这一条。该页的示例写明：只保留这些默认规则时，两台关联了 default 组的实例可以互访，但不能从互联网网关或 NAT 网关接收流量。要对外提供服务，应新建安全组并写上需要的允许，再关联到实例，而不是把默认组改成对全世界开放。

因此 AWS 上“什么规则都没加”至少有两种：新建安全组是入站全拒绝、出站全允许；default 组是入站只允许本组、出站全允许，并且在 VPC 已有 IPv6 时出站还包括 `::/0`。两种都不会因为你没有写 22 端口，就把 22 对 `0.0.0.0/0` 打开。22 被公网访问，一定是后来有人加了允许，或者使用的不是这两套默认。

### 22、3389 和分层示例

安全组概述页的最佳实践写明：只授权特定 IAM 主体创建和修改安全组；尽量少建安全组，同一组管理需求相近的资源；为 22 或 3389 添加入站时，只授权特定地址段。若指定 `0.0.0.0/0`（IPv4）和 `::/`（IPv6），任何地址都能用该协议访问实例。这里的 IPv6 写法按该页原文是 `::/`，不是 `::/0`。同一套 VPC 文档里，默认网络 ACL 和自定义网络 ACL 页把全部 IPv6 写成 `::/0`。两处不合并成一种“官方标准写法”，控制台里以你实际看到的前缀为准。该页还写：不要开放很大的端口范围；每个端口只对需要它的来源或目的开放；可以再做一份与安全组相近的网络 ACL，作为 VPC 里的另一层。

安全组规则页的示例把三层分开，且只使用允许规则：负载均衡安全组允许来自互联网的 HTTP 和 HTTPS，来源是 `0.0.0.0/0`；Web 服务器只允许来自负载均衡安全组的 HTTP 和 HTTPS；数据库服务器只允许来自 Web 服务器安全组的数据库请求。示例没有把数据库端口的来源写成 `0.0.0.0/0`。该页没有指定数据库必须是 3306 还是别的端口，不补端口号。

这次没有打开 Session Manager 或 EC2 Instance Connect 的专页，不把“必须改用会话管理器、可以不留 22”写成已经核对过的官方步骤。已经核对到的是：22 和 3389 只授权特定地址段，数据库来源用 Web 层的安全组，而不是全网。

### 网络 ACL 无状态，默认 ACL 和自定义 ACL 的起点不同

[Control subnet traffic with network access control lists](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html)（页上未见更新日期）写明网络 ACL 在子网边界允许或拒绝流量，没有额外费用。每个子网必须关联一个网络 ACL；没有显式关联时，用 VPC 的默认网络 ACL。一个网络 ACL 可以关联多个子网，一个子网同时只能关联一个。换绑之后，旧关联被去掉。

规则号从 1 到 32766，从最小号开始评估，命中就执行，不再看后面的规则。该页建议规则号按 10 或 100 的间隔来留，方便以后插入。评估发生在流量进入和离开子网时，不在子网内部转发时再评一次。网络 ACL 无状态：入站允许了请求，响应不会自动允许，必须有相应方向的允许。这和安全组相反。

网络 ACL 同样不能拦截发往 Route 53 Resolver（VPC+2，也称 AmazonProvidedDNS）的 DNS，也不能拦截实例元数据服务。元数据访问要到 EC2 用户指南里的实例元数据选项去管，那一页这次没有打开。DNS、DHCP、元数据、ECS 任务元数据、Windows 许可证激活、时间同步和默认路由器保留地址，也在网络 ACL 的不过滤列表里，和安全组那份列表相同。

[Default network ACL for a VPC](https://docs.aws.amazon.com/vpc/latest/userguide/default-network-acl.html)（页上未见更新日期）写明，VPC 自带的默认网络 ACL 允许关联子网的流量进出。入站规则 100 允许来自 `0.0.0.0/0` 的全部 IPv4。出站规则 100 在表里的类型写成 All traffic，目的 `0.0.0.0/0`，动作为 ALLOW。IPv6 的规则 101（入站源 `::/0`、出站目的 `::/0`，全部允许）只在创建 VPC 时就关联了 IPv6 CIDR，或后来关联了 IPv6 CIDR 时加入。若你已经改过某一方向的规则，再给 VPC 关联 IPv6 时，该页写明不会自动补上那条允许全部 IPv6 的规则。规则号为 `*` 的规则拒绝未匹配流量，不能删除。入站的 `*` 在表里分成 IPv4 的 `0.0.0.0/0` 和 IPv6 的 `::/0` 两行，出站同样有两行。默认 ACL 因为规则 100 已经允许全部 IPv4，`*` 平时轮不到；删掉 100 之后，未匹配的流量才会被 `*` 拒绝。

[Custom network ACLs for your VPC](https://docs.aws.amazon.com/vpc/latest/userguide/custom-network-acl.html)（页上未见更新日期）写明，每份网络 ACL 都有规则号为 `*` 的默认入站和默认出站，未匹配其他规则就被拒绝，`*` 不能删除。该页随后的 80、443、22 和临时端口表标明是示例，不是创建自定义 ACL 后自动生成的规则，不要当成出厂配置抄进账号。示例里的要点可以核对：

- IPv4 和 IPv6 分开评估。IPv4 规则不作用于 IPv6，反过来也一样。示例为 80 和 443 各写了一条 `0.0.0.0/0` 和一条 `::/0`。只加 IPv4 的 443，不会放行 IPv6 的 443。
- SSH 的示例来源是 `192.0.2.0/24`，不是 `0.0.0.0/0`。这是文档示例网段。
- 子网里的实例主动访问互联网时，回包要在入站允许临时端口；互联网上的客户端访问子网里的服务时，响应要在出站允许临时端口。示例用了 `32768-65535`。同一页还列出：许多 Linux 内核（含 Amazon Linux）是 32768–61000；Elastic Load Balancing、NAT 网关和 Lambda 是 1024–65535；Windows Server 2003 及更早是 1025–5000；Windows Server 2008 及以后是 49152–65535。该页说，要覆盖访问公网实例的各类客户端，可以开放 1024–65535，若要拒绝这个范围里的某些端口，拒绝规则号要小于那条宽范围允许。
- 若后端子网的网络 ACL 对来源 `0.0.0.0/0` 或该子网 CIDR 拒绝了全部流量，负载均衡无法对实例做健康检查。

[Network ACL rules](https://docs.aws.amazon.com/vpc/latest/userguide/nacl-rules.html)（页上未见更新日期）把规则拆成规则号、类型、协议、端口、入站的源或出站的目的、允许或拒绝。用命令行或 API 写入的 CIDR 会被收成规范形式，例如 `100.68.0.18/18` 会变成 `100.68.0.0/18`。同一页提醒：不要在一次操作里删掉旧规则又加进超过配额的新规则，否则可能出现旧的被删掉、新的没加上，子网突然不可达。配额数字这次没有打开配额页，不填。

安全组允许了 443，默认网络 ACL 的规则 100 也会允许。把子网改绑到一份只有 `*` 拒绝、还没写允许的自定义网络 ACL 上，安全组里的允许不会单独把流量放进来。反过来，默认网络 ACL 仍是允许全部时，只改安全组就够决定实例能不能被访问；这时网络 ACL 没有提供第二层收紧。

## Microsoft Azure

以下来自 learn.microsoft.com 的全球文档，通读的是中文页。由世纪互联运营的 Azure 没有打开，不把下面的默认优先级和平台地址套到那套环境。

### 网络安全组有状态，规则有优先级

[Azure 网络安全组概述](https://learn.microsoft.com/zh-cn/azure/virtual-network/network-security-groups-overview)（页上未见更新日期）写明，网络安全组用来筛选虚拟网络里 Azure 资源之间的流量，规则可以允许或拒绝入站和出站。每条规则有名称、优先级、源或目标、协议、方向、端口范围和允许或拒绝。优先级是 100 到 4096 的数字，越小越优先。命中一条之后停止，数字更大的规则不再处理。默认规则的数字最大，所以自定义规则先被处理。同一优先级、同一方向不能有两条规则。

源或目标可以是 Any、单个 IP、CIDR（页上例子是 `10.0.0.0/24`）、服务标记或应用程序安全组。入站在公网 IP 转成专用 IP 之后处理，出站在专用 IP 转成公网 IP 之前处理。因此规则里写的是专用地址，不是资源的公网 IP。增强型规则可以在一条里写多个 IP 和多个端口，但一条规则不能写多个服务标记或多个应用程序安全组。该页写明增强型规则只适用于资源管理器部署模型，经典部署模型不能在一条规则里写多个地址段或多个端口。经典部署的菜单这次没有按产品线单独打开，不补一套经典网络的默认表。

协议可以是 TCP、UDP、ICMP、ESP、AH 或 Any。ESP 和 AH 在门户里不可用，可以通过 ARM 模板使用。Any 包含 TCP、UDP 和 ICMP。

网络安全组有状态，依据是流记录。例如出站允许了访问任意地址的 80，响应不需要再写一条入站。入站允许了某个端口，响应也不需要再写出站。删除一条允许之后，已经建立的连接不断；新连接才受影响。该页的例子是：删掉允许 SSH 的规则后，当前 SSH 会话仍在，再发起的新 SSH 会被拒绝。新规则和更新后的规则只作用于新连接。

### 每个新建网络安全组都带的默认规则

概述页写明，下面这些规则在每个你创建的网络安全组里都有，不能删除，可以靠更高优先级（更小的数字）覆盖。

入站：

- AllowVNetInBound，优先级 65000，源和目标都是服务标记 VirtualNetwork，端口 0–65535，协议 Any，允许。
- AllowAzureLoadBalancerInBound，优先级 65001，源是 AzureLoadBalancer，源端口 0–65535，目标 `0.0.0.0/0`，目标端口 0–65535，协议 Any，允许。
- DenyAllInbound，优先级 65500，源和目标都是 `0.0.0.0/0`，端口 0–65535，协议 Any，拒绝。

出站：

- AllowVnetOutBound，优先级 65000，源和目标都是 VirtualNetwork，端口 0–65535，协议 Any，允许。
- AllowInternetOutBound，优先级 65001，源 `0.0.0.0/0`，目标是服务标记 Internet，端口 0–65535，协议 Any，允许。
- DenyAllOutBound，优先级 65500，源和目标都是 `0.0.0.0/0`，端口 0–65535，协议 Any，拒绝。

VirtualNetwork、AzureLoadBalancer、Internet 是服务标记，不是某一条固定的客户 IP。该页写 `0.0.0.0/0` 表示所有 IP 地址，门户、CLI 和 PowerShell 可以用 `*` 或 Any。默认规则表里没有 `::/0` 行。这次没有另开一页去核对 IPv6 默认规则是否单独存在，不把“DenyAllInbound 已经覆盖全部 IPv6”写成该表的原文。若虚拟机启用了 IPv6，入站和出站的 IPv6 规则要在当前 NSG 里单独看。

有了这套默认规则之后，一台只关联了 NSG、没有自定义允许的虚拟机：来自虚拟网络内部的流量可以被 AllowVNetInBound 放行；来自 Internet、目的端口是 22 或 3389 或 3306 的入站，匹配不到更高优先级的允许，会落到 DenyAllInbound。出站访问 Internet 会被 AllowInternetOutBound 放行，除非你写了更小数字的拒绝。这和“NSG 默认把出站也全部拒绝”不同。出站的拒绝全部是 65500，排在允许 Internet 的 65001 之后。

### 子网和网卡是两道，没关联时也不等于允许入站

[网络安全组如何筛选网络流量](https://learn.microsoft.com/zh-cn/azure/virtual-network/network-security-group-how-it-works)（页上未见更新日期）写明，同一个 NSG 可以关联到任意多个子网和网络接口。入站先评估子网关联的 NSG，再评估网卡关联的 NSG。子网 NSG 已经拒绝的流量，不会再送到网卡 NSG。两边都有关联时，要让 Internet 访问虚拟机的 TCP 80，子网 NSG 和网卡 NSG 都要有允许。只有子网 NSG 时，子网里的虚拟机一起接受这套允许或拒绝。只有网卡 NSG、子网没有时，流量先进入子网，再由网卡 NSG 决定。

出站顺序相反：先网卡，再子网。网卡 NSG 若拒绝了 TCP 80 出站，子网 NSG 不会再评估这段流量。要拒绝虚拟机的 80 出站，两边任意一边有拒绝即可。

同一子网里的虚拟机默认能通信，是因为 AllowVNetInBound 和 AllowVnetOutBound。若在子网 NSG 上加了拒绝全部入站和出站，子网内的虚拟机也不能再互访。

该页的 VM4 示例是：子网和网卡都没有关联 NSG。入站被阻止。页上写，带标准公共 IP 的虚拟机在这种情况下默认是安全的；要让 Internet 的流量进来，必须给子网或网卡关联网络安全组。出站在这个示例里不受 NSG 限制，可以从虚拟机自由流出。因此“没有 NSG”和“有一个只含默认规则的 NSG”结果不同。没有 NSG 时，该示例的入站进不来，但出站也不受 AllowInternetOutBound / DenyAllOutBound 这套规则约束。加上 NSG 之后，入站才出现“虚拟网络允许、其余拒绝”，出站才出现“Internet 允许、其余拒绝”。

该页建议不要同时把 NSG 关联到子网和网卡，只选一层，避免两层规则叠在一起难以排查。有效安全规则可以在网络接口上查看；网络观察程序的 IP 流验证可以指出是哪一条规则允许或拒绝。这些是该页写明的排查入口。

安全管理员规则写在概述页，来自 Azure 虚拟网络管理器，优先级高于网络安全组，先被评估。动作为允许的管理员规则，还会继续按匹配的 NSG 规则评估。动作为始终允许的管理员规则直接把流量送到资源，不再看可能冲突的 NSG。动作为拒绝的管理员规则在本层就停下，不会把流量交给 NSG。因此 NSG 里把 22 收成办公网之后，若订阅里还有一条始终允许或更早的拒绝，结果以管理员规则为准。管理员规则专页这次没有按配置步骤打开，不写怎么在虚拟网络管理器里下发。

### 平台流量和 22、3389

概述页写，DHCP、DNS、IMDS 和运行状况监视使用主机虚拟 IP `168.63.129.16` 和 `169.254.169.254`。默认情况下这些服务不受你配置的 NSG 限制，除非针对具体服务使用服务标记。该页给出的、用来拒绝这类平台通信的标记是 AzurePlatformDNS、AzurePlatformIMDS、AzurePlatformLKM。不把“在 NSG 里拒绝 `0.0.0.0/0`”理解成已经挡住元数据地址。

负载均衡池里的虚拟机，NSG 看到的源是客户端，不是负载均衡器的地址；目标是虚拟机，不是负载均衡器。把 HDInsight、应用服务环境、虚拟机规模集等部署进子网之前，该页要求先看服务自己的端口，否则拒绝会让服务起不来。具体端口清单在“可部署到虚拟网络中的服务”那一页，这次没有打开，不逐个列端口。

出站 TCP 25 在概述页是平台行为，不是 NSG 默认规则表里的一行。该页建议用经过身份验证的 SMTP 中继，通常是 TCP 587，也可以是其他端口，并举例 Exchange Online Protection 和 SendGrid。2017 年 11 月 15 日之后创建的订阅，可能不能直接用端口 25 发信；企业协议、开发/测试、即用即付、MSDN 等类型的差异该页分别写了。这里不写如何申请放开 25。需要从虚拟机发信时，按该页使用中继，而不是把 25 对公网放开。

概述页没有一份“22 和 3389 不得对 Internet 开放”的独立最佳实践清单。从默认规则可以直接核对的是：没有更高优先级的允许时，Internet 入站会被 DenyAllInbound 拒绝，其中包括 22、3389 和数据库端口。一旦有人加了来源为 Internet 或 `0.0.0.0/0`、优先级小于 65500 的允许，默认拒绝就不再作用于已经命中的那条流量。how-it-works 的 80 端口示例是这种允许要写在子网和网卡两侧（如果两侧都关联了 NSG）的说明，不是要求把 80 对公网开放。

这次没有打开 Azure Bastion 专页，不写堡垒机的子网掩码和 SKU。已经核对到的收紧方式是：不写来源为 Internet 的管理端口允许；需要分层时只在子网或只在网卡关联 NSG，并看有效规则。

## Google Cloud

以下来自 cloud.google.com 与 docs.cloud.google.com。VPC 防火墙规则、规则评估顺序，以及一份说明隐含规则和 IAP 的教程，都已打开。

### 规则属于网络，执行在实例上

[VPC firewall rules](https://cloud.google.com/vpc/docs/firewalls)（页上未见更新日期；打开的地址是 `cloud.google.com/vpc/docs/firewalls`）写明：VPC 防火墙规则作用于一个项目里的一个网络。规则在网络上定义，连接按实例允许或拒绝。实例还没启动、来宾操作系统怎么配，只要规则处于启用状态，就会执行。可以把它理解成既位于实例与其他网络之间，也位于同一网络里的实例之间。

每条规则只处理一个方向，入方向或出方向，不能一条规则两边都管。不写方向时，默认是入方向。动作是 `allow` 或 `deny`。可以禁用规则而不删除，便于排查。省略目标时，规则作用于该 VPC 里的全部实例；也可以用网络标记或服务账号限定目标。网络标记和目标服务账号不能写在同一条规则里。该页建议，若要严格控制规则作用到哪些虚拟机，用服务账号而不是网络标记，因为能编辑实例的主体就可以改标记。服务账号防火墙规则作用在 GKE 节点上，不是 Pod 上。

规则有状态。任一方向允许了连接之后，与该连接匹配的回包也被允许，不能再写一条规则去拒绝这段回包。回包要符合原来的五元组，只是源和目的的地址、端口对调。跟踪状态在至少每 10 分钟有一个包时视为仍有效。IPv4 连接跟踪覆盖 TCP、UDP、SCTP 和 ICMP；IPv6 覆盖 TCP、UDP、SCTP 和 ICMPv6。分片连接被允许后，回程只自动放行第一个分片，后续分片要另加规则。该页还写，更改启用状态、新建强制规则，或把以前允许的流量改成拒绝时，Cloud NGFW 只对新连接执行；已有连接保持。

一条规则只能包含 IPv4 范围或 IPv6 范围，不能混写。入方向如果省略来源，默认来源是 `0.0.0.0/0`，该页写明这个默认值不包含 IPv6。出方向如果省略目的，默认目的同样是 `0.0.0.0/0`，也不包含 IPv6。要匹配 IPv6，必须另行写 IPv6 范围。端口只支持目的端口，不支持按源端口写规则。只写一个数字会被当成 IANA 协议号，例如单独的 `80` 是协议 80，不是 TCP 80；TCP 80 要写成 `tcp:80`。

优先级是 0 到 65535，包含两端，不写时默认 1000。数字越小越优先。同一目标上，更高优先级的宽规则会压过更低优先级的窄规则。例如一条优先级更高的“全部协议、全部端口、允许”，会压过同一目标上优先级更低的“拒绝 TCP 22”。同优先级时，deny 覆盖 allow。同优先级且动作相同的多条规则，结果相同，但启用日志时到底记录哪一条并不确定；该页建议要稳定的日志顺序时使用互不相同的优先级。防火墙策略规则的优先级上限更高，是 0 到 2,147,483,547，而且在同一策略里必须唯一。VPC 防火墙规则允许多条共用一个优先级。

### 隐含动作，以及 default 网络预置的 22 和 3389

防火墙规则页写：若没有任何 VPC 防火墙规则适用，评估可能走到最后一步，由 Cloud NGFW 按方向和目标类型使用隐含动作。具体顺序在评估页。该页的入方向、出方向示例直接使用了“隐含拒绝入方向”和“隐含允许出方向”这两个名字：没有入方向允许时，带外网 IP 的虚拟机仍然进不来；没有出方向规则时，隐含允许会让它向外发送，回包因为有状态而允许。

[防火墙规则评估顺序](https://docs.cloud.google.com/firewall/docs/firewall-policies-rule-eval-order)（页上未见更新日期）把网络防火墙策略的执行顺序分成两种。默认是 `AFTER_CLASSIC_FIREWALL`：分层防火墙策略、区域系统防火墙策略、VPC 防火墙规则、全球网络防火墙策略、区域网络防火墙策略，最后才是隐含动作。`BEFORE_CLASSIC_FIREWALL` 把全球和区域网络防火墙策略放到 VPC 防火墙规则之前，隐含动作仍在最后。更改顺序的命令该页写的是 `gcloud compute networks update` 的 `--network-firewall-policy-enforcement-order`。

最后一步的隐含动作，评估页按目标区分，没有在这一节重复优先级数字：

- 入方向、目标是虚拟机网卡：deny。
- 入方向、目标是内部应用负载均衡或内部代理网络负载均衡的转发规则：allow。
- 出方向：allow。

[配置全球网络防火墙策略的教程](https://cloud.google.com/firewall/docs/configure-global-fw-policies)（页上未见更新日期）把隐含规则写成两条 IPv4 规则，并给出优先级 65535：出方向允许，目的 `0.0.0.0/0`，虚拟机可以向任意目的发送，该页注明仍会受到 Google Cloud 另行阻止的流量限制；入方向拒绝，来源 `0.0.0.0/0`。教程开头还写，自定义 VPC 默认出方向允许、入方向拒绝。65535 这个数字来自教程页，不来自评估页的最后一步小节。教程写的是 IPv4。不把“同一条 65535 已经拒绝全部 IPv6 入方向”补进教程没有写的范围。

default 网络另有一套可删除、可修改的预置规则，优先级都是 65534，因此高于教程页所写的隐含规则 65535，会先于隐含拒绝命中：

| 规则名 | 方向 | 优先级 | 来源 | 动作 | 协议和端口 |
| --- | --- | --- | --- | --- | --- |
| `default-allow-internal` | 入方向 | 65534 | `10.128.0.0/9` | 允许 | TCP 0–65535、UDP 0–65535、ICMP |
| `default-allow-ssh` | 入方向 | 65534 | `0.0.0.0/0` | 允许 | TCP 22 |
| `default-allow-rdp` | 入方向 | 65534 | `0.0.0.0/0` | 允许 | TCP 3389 |
| `default-allow-icmp` | 入方向 | 65534 | `0.0.0.0/0` | 允许 | ICMP |

防火墙规则页写明，这些规则让你可以用 `ssh`、`scp`、`sftp` 连接实例，用 RDP 连接实例，以及使用 `ping`。来源都是 `0.0.0.0/0`，不是某个办公网。表里没有 `::/0`。使用 default 网络时，只把某条自定义规则的 IPv4 来源收紧，不会自动删掉 `default-allow-ssh` 和 `default-allow-rdp`。这两条仍在，22 和 3389 就仍对全部 IPv4 开放。其他网络可以按该页自行创建类似规则；该页没有写“每个新建的自定义 VPC 都会带上这四条”。教程页对自定义 VPC 的描述是入方向由隐含规则拒绝。

防火墙规则页的最佳实践是：默认阻止，只允许需要的协议和端口；用分层防火墙策略在组织或文件夹挡住不应出现的流量；允许规则尽量用虚拟机的服务账号来限定目标；若必须按 IP 写，尽量合并，而不是一台虚拟机一条；用防火墙策略、地址组、FQDN 对象或地理位置对象做更细的控制。后两类可能产生 Cloud Next Generation Firewall Standard 的数据处理费用，该页只提示可能收费，没有给出单价，这里不补价格。VPC 防火墙规则日志和 Firewall Insights 可以核对规则是否按预期命中，日志也可能产生费用。该页建议有选择地开。

元数据服务器不受 VPC 防火墙规则和分层防火墙策略约束。IPv4 地址是 `169.254.169.254`，IPv6 地址是 `fd20:ce::254`。DHCP、DNS、实例元数据和 NTP 走这台服务器。发往实例自己网卡地址、且留在虚拟机内部的包，同样不受这些规则约束。

### IPv6、IAP 和平台对 25 端口的限制

因为一条规则不能同时写 IPv4 和 IPv6，default 网络预置规则的来源又是 `0.0.0.0/0`，所以收紧 IPv6 入方向要另找 IPv6 规则。省略来源并不会生成一条覆盖 IPv6 的“任意来源”。若你后来加了一条来源为 `::/0` 的允许，它只匹配 IPv6，不会替代 `default-allow-ssh` 的 IPv4。两个地址族都要在规则列表里看到，才算核对完。

教程页给出了一种不给虚拟机外网 IP、仍能管理的做法：用 Identity-Aware Proxy 的 TCP 转发。要让 IAP 连上虚拟机，防火墙规则需要允许来自 `35.235.240.0/20` 的入方向；IPv6 虚拟机使用 `2600:2d00:1:7::/64`。端口是你希望经 IAP 访问的端口，教程的例子是 SSH 的 22 和 RDP 的 3389。这是该教程页上的地址和端口，不是一条可以套到其他云的白名单。没有外网 IP 的虚拟机要访问公网下载软件时，同一教程使用 Cloud NAT。NAT 网关空转是否计费，见闲置公网资源一文，这里不重复。

SMTP 的 TCP 25 在防火墙规则页是另一项平台限制，不是 VPC 防火墙规则表里的一行。默认情况下，发往外部 IP 的 TCP 25 会被阻止，包括发往其他 Google Cloud 资源的外部 IP；发往内部 IP 的 TCP 25 不受这条限制。该页写明 TLS 的 465 和 587 不在这项阻止之内。项目是否已被允许发送未加密的大量邮件，要看 VPC 网络页或防火墙策略页上的提示。不想让实例对外发 25，可以写一条出方向拒绝，或在分层策略里拒绝。这里不写如何让平台去掉这项阻止。

代理型负载均衡的转发规则接受哪些协议和端口，由转发规则决定，VPC 防火墙规则不管这一段；防火墙规则管的是代理到后端的流量。直通型负载均衡则由防火墙规则决定哪些协议和端口能到达后端。Cloud VPN 网关接受哪些端口，也不由这些防火墙规则决定。GKE 会在创建集群、Service 和 Ingress 时自动创建防火墙规则。自动规则的名单在 GKE 文档，这次没有打开，不把某条自动规则说成可以随便删。

## 检查清单

按这个顺序看。每一步都先分清账号在中国站、国际站还是全球文档对应的环境，再改规则。腾讯云国际站、AWS 中国区和世纪互联运营的 Azure 这次没有打开。

1. 列出每台需要远程管理或对外提供服务的实例，记下它的安全组、网络安全组或防火墙规则，以及子网有没有第二层 ACL。阿里云同时看弹性网卡上的安全组和交换机上的网络 ACL。腾讯云同时看实例安全组和子网网络 ACL。AWS 同时看安全组和子网网络 ACL。Azure 看子网和网卡各关联了哪个 NSG，以及是否还有虚拟网络管理器的安全管理员规则。Google Cloud 看 VPC 防火墙规则，再按评估顺序看分层策略和网络防火墙策略。只截一张安全组的允许列表，会漏掉另一层。
2. 把 `0.0.0.0/0` 和 IPv6 全网地址分开搜。阿里云、腾讯云文档里的 IPv6 全网写法是 `::/0` 或 `0::0/0`。AWS 安全组最佳实践页写的是 `::/`，网络 ACL 页写的是 `::/0`。Google Cloud 省略来源时默认只有 `0.0.0.0/0`，不包含 IPv6。Azure 这次读到的默认规则表只有 `0.0.0.0/0`，没有 `::/0` 行。IPv4 已经收成办公网，不能说明 IPv6 也收了。
3. 认出“默认”实际放行了什么。阿里云默认安全组的可见入方向是 22、3389 和 ICMP（IPv4）对 `0.0.0.0/0` 允许；控制台创建安全组时，常见问题页另写了可能包含 80 和 443。腾讯云空规则组是全部拒绝，但“放通全部端口”模板、放通 22/80/443/3389/ICMP 的模板，以及 API 未指定安全组时的默认安全组，都会放行。一键放通同时包含 IPv4 和 IPv6。AWS 的 default 安全组不会对公网开放 22，但默认出站是全部允许；default 网络 ACL 的规则 100 允许全部 IPv4。Azure 新建 NSG 的入站最终是否拒绝，取决于有没有更小数字的允许；出站默认允许 Internet。Google Cloud 的 default 网络有 `default-allow-ssh` 和 `default-allow-rdp`，来源 `0.0.0.0/0`，优先级 65534。
4. 管理端口只保留必要来源。阿里云案例对 22 和 3389 使用具体 IP；Workbench 的前缀以中国站或国际站当前页为准，两边公网前缀不同。AWS 最佳实践要求 22 和 3389 使用特定地址段，并避免大端口范围。Google Cloud 若改用教程中的 IAP，来源是该页的 `35.235.240.0/20` 或 IPv6 的 `2600:2d00:1:7::/64`，而不是 `0.0.0.0/0`。腾讯云添加规则页提供“当前登录 IP”作为来源，这是控制台识别到的当前公网 IP，不是永久白名单。
5. 数据库端口不要和 Web 端口放在同一条全网允许里。阿里云案例把 3306、1521、1433、5432、6379 的来源写成具体 IP、CIDR 或安全组；企业级安全组不能使用安全组 ID 作为授权对象。AWS 示例把数据库来源写成 Web 服务器的安全组，把 `0.0.0.0/0` 留在负载均衡的 80/443。腾讯云这次打开的页面没有数据库端口示例，按“未添加的入站默认拒绝”来核对，不要从模板名称推断 3306 的状态。
6. 第二层是无状态时，补上响应方向再做连通性测试。阿里云网络 ACL、腾讯云网络 ACL、AWS 网络 ACL 都要为回包写规则。临时端口范围以各云已打开的页面为准：阿里云和 AWS 写了 Linux、Windows、NAT 的区间，腾讯云规则概述没有写数字。只放行服务端口的一侧，请求可能进去，回包在离开子网时被默认拒绝或系统拒绝丢掉。
7. 改规则前先留备份，并想到已有会话。阿里云使用安全组页可以导出 JSON 或 CSV，也有安全组快照，恢复会用快照完全覆盖当前规则。腾讯云概述建议先导出，有问题再导入。阿里云写明行为不变时已有会话可以保持，依赖组内互通时要先加入新组、等待约 10 秒再离开。Azure 写明删掉 SSH 允许后旧会话还在，新连接才被拒绝。Google Cloud 写明拒绝以前允许的流量时，只影响新连接。AWS 规则页把已有流量指向连接跟踪，该专页这次没打开。验证时新建一条连接，不要只看已经连着的会话。
8. 阿里云普通安全组若仍是组内互通，同组内网会被不可见规则放行，自定义拒绝拦不住。不需要互访时改成组内隔离。多个安全组里只要有一个仍是组内互通，使用安全组页写明实例之间仍可内网互通。企业级安全组没有这条互通，出方向未命中也会拒绝，应用若要访问外网，要有明确的出方向允许。
9. 负载均衡后面的实例，不要只在实例安全组上判断公网是否进得来。阿里云安全组默认放行 SLB 转来的流量，拦不住，要看负载均衡自己的安全组或访问控制。AWS 示例把公网 80/443 放在负载均衡安全组，Web 安全组只引用负载均衡。Azure 对负载均衡池里的虚拟机使用客户端的源地址。Google Cloud 对代理型负载均衡的转发规则本身不靠 VPC 防火墙规则限制监听端口。
10. 改完后看有效规则，而不是只看刚保存的那一条。Azure 可以在网络接口上看有效安全规则，并用 IP 流验证。阿里云使用安全组页写了安全组规则诊断，能检查 80、443、22、3389、8080 或自定义端口是否放行。AWS 自定义网络 ACL 页提到 Reachability Analyzer 可以指出是不是 ACL 挡住了路径，分析器的专页这次没有打开。Google Cloud 可以用防火墙规则日志核对命中，同时注意该页写的日志费用。

## 常见坑

- 把阿里云默认安全组当成“还没加规则所以是拒绝”。默认安全组是普通安全组，入方向另外允许任意 IPv4 访问 22、3389 和 ICMP。常见问题页还写，控制台创建安全组时的默认规则可能包含 80 和 443。企业级安全组未命中才是入方向和出方向都拒绝。三种不要用同一个名字。
- 只改安全组，或只改网络 ACL。阿里云新建的网络 ACL 带允许全部 IPv4 的自定义规则，绑定之后子网边界仍是放行，直到你改掉它；系统拒绝排在最后。腾讯云新建的网络 ACL 则是默认拒绝 `0.0.0.0/0`，只绑定、不在它上面加允许，进出子网会落到拒绝。AWS 默认网络 ACL 的规则 100 允许全部 IPv4，自定义 ACL 的 `*` 拒绝未匹配流量。方向相反的两套默认，不能互相套用。
- 在无状态的 ACL 上只复制安全组的入站允许。回包的目的端口是临时端口。阿里云和 AWS 都要求另写响应方向。腾讯云同一页既写匹配成功则允许通过，又在示例里把拒绝放在允许上面；按位置更前的规则生效来排拒绝和允许，并给回包留出站允许。不要把安全组的“回包自动通过”用到 ACL 上。
- IPv4 收紧了，IPv6 仍是一键放通或 `::/0`。腾讯云一键放通同时包含 IPv4 和 IPv6。阿里云案例把 `::/0` 和 `0.0.0.0/0` 都标成高风险。AWS 默认安全组在 VPC 具备 IPv6 CIDR 时会增加出站 `::/0`；若已经改过默认网络 ACL，后来再关联 IPv6，允许全部 IPv6 的规则 101 不会自动补上。Google Cloud 一条规则不能同时写两个地址族，default 网络的 SSH/RDP 预置规则来源是 `0.0.0.0/0`。
- 阿里云同优先级才会让拒绝排在允许前面。优先级 1 的 `0.0.0.0/0` 允许会先命中并停止，后面优先级 100 的拒绝不会再生效。案例页把 MySQL 公网拒绝的优先级写成 100，只在现有允许没有更小的优先级号时才碰得到。默认安全组的 22 和 3389 本身就是优先级 100。
- 普通安全组的组内互通绕过自定义拒绝。要限制同组内网，先改组内隔离。企业级安全组不能授权安全组 ID，案例里“Web 组访问数据库组”的写法只适用于普通安全组。一块网卡也不能同时加入两种类型。
- 中国站和国际站的配额、Workbench 前缀不要混用。中国站安全组规则页写单张网卡规则上限 2,000，使用安全组页写 1,000，国际站规则页写 1,000。Workbench 公网前缀，中国站案例是四段具体 CIDR，国际站案例是 `161.117.0.0/16`，私网两边都写了 `100.104.0.0/16`。以账号所在站点的当前页为准。
- AWS 安全组不能写拒绝。想“默认允许、再拒绝几个端口”要写在网络 ACL 上，并且拒绝的规则号要更小。多个安全组是把允许规则汇总，不是阿里云那种按优先级穿插拒绝。新建安全组的出站是全部允许，只删入站并不等于限制了实例向外连接。
- Azure 子网 NSG 和网卡 NSG 叠在一起。入站要两边都允许才到得了虚拟机；出站一边拒绝就会停。how-it-works 页建议只关联一层。没关联任何 NSG 时，该页的标准公共 IP 示例是入站被阻止，不要据此认为出站也走了 DenyAllOutBound。安全管理员规则的“始终允许”或“拒绝”会在 NSG 之前结束评估。
- Google Cloud 的 `default-allow-ssh` 优先级是 65534，比教程页写的隐含拒绝 65535 更优先。不删除或改掉这条，另写一条优先级 1000 的拒绝并不能挡住 22，因为 65534 的数字更小、更先命中。更宽的高优先级允许也会压过更窄的低优先级拒绝。同优先级才是 deny 覆盖 allow。
- 负载均衡或平台地址不走你以为的那条实例规则。阿里云安全组放行 SLB 后端流量和 MetaServer。AWS 安全组和网络 ACL 都不过滤元数据、DNS 和 DHCP。Azure 默认不限制 `168.63.129.16` 和 `169.254.169.254`。Google Cloud 元数据服务器不受防火墙规则约束。在安全组里拒绝全部，不会自动变成“实例不能访问元数据”。
- 已有会话还在，不代表新规则已经生效。阿里云、Azure、Google Cloud 已打开的页面都写了已建立连接可以继续。用旧的 SSH 窗口做测试，会得到仍然连通的假象。断开后重新连接，或从一台尚未建立会话的来源访问，再判断规则。
- 把这份全球文档直接用于没打开的站点。腾讯云国际站两个链接是 404。AWS 中国区文档和世纪互联运营的 Azure 没有打开。阿里云金融云、政务云只在中国站网络 ACL 的地域表里看到，不套到国际站。
